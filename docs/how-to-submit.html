How to submit, when an eligible file exists

Do not upload any current file, including the S1 candidate above. These instructions are conditional; neither inspection nor a format pass bypasses the two recorded stops (holdout below the incumbent; literal duplicate stop against the lattice witness, a flagged protocol irregularity).

Official rules, verified 2026-10-29 (NLR rules PDF, §1.1 and §3.2): one entry per competitor; a single GeoTIFF with a single raster layer at 100 m; submission limit three submissions per week; generative-AI use must be described in the narrative. The problem page (page 967) specifies values between 0 and 1, float32, and null or NaN outside the bounds.

  1. Run a newly assigned lane using the shared feature stack, evaluator and writer. Stop immediately if the pre-placement surface is a duplicate. Test every input feature alone for leakage; AUC over 0.90 is suspect.
  2. Use buffered whole-segment hide-and-recover; build all catalogue features from visible faults only and mask visible faults pixel-exactly. Compare pooled DTI against the current same-fold incumbent with a paired 95% interval. An uncalibrated holdout is not a leaderboard estimate.
  3. Recheck the exact final TIFF against the complete current registry and authenticate the organizer sample. Verify a single float32 band, matching CRS/shape/transform, and no non-finite or out-of-range values inside the actual footprint.
  4. Only after every automated gate passes, a separate selector checks the account quota. The official rules describe up to three scored attempts per week and one final selection per participating entity.
  5. Then download the .tif, verify its SHA-256, sign in to the DrivenData submissions page, choose the file, and use the recorded unique name and a short note no longer than 140 characters. The official problem page specifies a GeoTIFF; ZIP upload acceptance was not verified. Save the actual organizer receipt; do not promote a projection into a score.

Fixing the portal error “Predicted values must be in range [0, 1]” (evidence-based, 2026-10-31)

The error is not caused by out-of-range pixels in the research files: every published TIFF in this repo is finite and inside [0, 1] (saved-byte inventory: public-downloads audit). What the audit of 10 published files plus the pinned registry shows:

  • Owner-scored files use both exterior conventions. The 0.2778 site champion and its GEMSDOE30/33/36 relatives use finite zeros outside the footprint with a nodata=None tag; GEMSDOE24/27/28/31-style files use NaN outside with a nodata=NaN tag. Both styles have owner-reported scores, so the exterior value alone cannot be the portal check.
  • The only downloadable file with a user-reported portal range failure (H-F, 2026-10-30) had a nodata=NaN TAG while containing zero NaN pixels. Reading the file with masked I/O therefore leaves every cell unmasked and the reader may propagate the declared NaN sentinel — a plausible trigger for a server-side “NaN not in [0, 1]” message. This is a hypothesis, unverified against the portal.
  • Practical guidance if a portal range error appears: re-upload the identical pixel content as nodata=None with finite zeros outside the footprint (the champion convention used by the S1 candidate); do not declare a nodata value that occurs nowhere in the array; keep the TIFF single-band float32 with the sample's exact CRS/shape/transform; upload the .tif itself rather than the ZIP.
